# 트리거 파라미터 설계 근거 (M3)

> **작성일**: 2026-06-25 · **백로그**: 잔여백로그 §4 M3 · **대상 코드**: `backend/app/routine_trigger.py`
> **목적**: 트리거 알고리즘 상수의 설계 근거를 문서화하고, 임상 절대근거가 아닌 heuristic임을 명시하며, 향후 튜닝을 M2 지표로 닫는 폐루프를 정의한다.

## 1. 현재 파라미터

| 상수 | 값 | 코드 |
|------|----|----|
| `TRIGGER_THRESHOLD` | 3회 | `routine_trigger.py:19` |
| `LOOKBACK_DAYS` | 7일 | `routine_trigger.py:21` |
| `COOLDOWN_DAYS` | 3일 | `routine_trigger.py:20` |
| 가중치 | mood 0.3 / 키워드 빈도 0.7 | `_calculate_trigger_score` |

## 2. 설계 근거 (heuristic)

각 값은 **임상시험으로 검증된 절대 임계가 아니라**, 제품 행동설계상의 합리적 출발점이다.

- **LOOKBACK 7일**: 주간 생활 리듬에 맞춰 "최근 경향"을 본다. PHQ-9의 회상 기간(2주)보다 짧게 잡아 더 민감하게 반응하되, 데이터 희소로 인한 노이즈와 균형을 맞춘다.
- **THRESHOLD 3회**: 7일 중 같은 감정 키워드 3회 이상 = 우연한 1~2회 변동이 아니라 **반복되는 신호**로 본다. 과트리거(루틴 폭주)를 막는 보수적 컷오프.
- **COOLDOWN 3일**: 같은 키워드가 연속 트리거되어 루틴이 쏟아지는 것을 막고, 사용자가 새로 배정된 루틴에 **적응할 시간**을 준다.
- **가중 0.3 / 0.7**: 키워드 빈도(직접적 반복 신호)를 주(主, 0.7), mood_score(보조 맥락)를 종(從, 0.3)으로 둔다. 무엇을 다룰지는 키워드가 정하고, mood는 순위에만 영향.

## 3. 한계

- **임상 근거 0**: 위 값들은 합리적 추정일 뿐, 효과가 데이터로 검증되지 않았다.
- **mood 가중 무력화(R1 연계)**: 트리거 발동 여부는 `freq >= THRESHOLD`(빈도 컷)로만 결정되고, mood 가중(0.3)은 발동 후 키워드 **순위**에만 작용한다. 즉 mood_score는 "어떤 키워드를 트리거할지" 선택에 사실상 영향이 적다. 이는 [잔여백로그 §2 R1]에 별도 항목으로 있으며, 고치려면 발동 조건 자체를 바꾸는 설계 변경이라 단독 수정 위험이 있어 보류 상태다.
- **규제**: 이 파라미터는 **내부 루틴 배정용**이며 진단 임계가 아니다. 어떤 값도 사용자에게 중증도·진단으로 제시되지 않는다.

## 4. 튜닝 폐루프 (M2 연계)

파라미터는 운영 데이터로 점진 조정한다. M2 운영자 지표(`scripts/usage_report.py`)의 **트리거 작동 빈도**를 모니터링한다.

- **과트리거 신호**: 일별 트리거 발동 수가 과도하거나 특정 키워드가 과대 → THRESHOLD 상향 또는 COOLDOWN 연장 검토.
- **저트리거 신호**: `assignments_by_source`의 `trigger`가 거의 0 → THRESHOLD 하향 또는 LOOKBACK 연장 검토.
- 조정 시 `_calculate_trigger_score`/`_evaluate_triggers` + `test_trigger` 동반 수정, 설계문서(C-5) 합의 선행.

> 결론: 현재 값은 검증된 정답이 아니라 **모니터링 가능한 출발점**이다. M2 지표가 폐루프의 관측 축을 제공한다.
