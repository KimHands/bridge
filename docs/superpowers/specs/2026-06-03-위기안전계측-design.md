## 1. 목적

위기·안전 방어선이 **실제로 얼마나 작동하는지**를 익명 집계해, 안전 개선 루프를 닫는다.
현재 `needs_professional_flag`조차 로깅·통계에 연결되지 않아 "방어선이 며칠에 몇 번 작동했는지" 아무도 모른다.

비목표(이번 사이클 제외):
- 클릭 전환(핫라인 `tel:`/병원 CTA **클릭**) — 모바일 이벤트 발신 필요 → 다음 사이클.
- 개별 사용자 위기 이력 추적 — "물리적 분리" 원칙상 의도적 미지원.
- 조회 엔드포인트/대시보드 — role 시스템 부재. 적재만, 조회는 운영자 SQL.

## 2. 결정 요약 (brainstorming)

| 결정 | 선택 | 이유 |
|---|---|---|
| 익명성 | **완전 익명** (user_id 미저장) | 정신건강 데이터 물리적 분리·규제 방어. 집단 지표로 충분 |
| 범위 | **백엔드 자동 계측만** | 서버가 이미 아는 발생·노출·가드발동. 클릭은 분리 |
| 적재 형태 | **사전집계 카운터** | 개별 레코드 부재 → 완전 익명 부합, 행 최소 |
| 이벤트 종류 | **5종** | 각자 다른 방어선. 한 요청당 상호배타적 1카운트 |
| 조회 | **적재만 + SQL** | M1 본질은 "미연결"을 연결. 공격면 비증가, YAGNI |

## 3. 데이터 모델

신규 테이블 **`safety_event_counters`** (`app/models/safety_metric.py`):

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | UUID PK | `default=uuid4` |
| `event_type` | String(40) | 5종 중 하나 |
| `day_bucket` | Date | **KST 기준** 날짜 (시간 절삭 → 익명) |
| `count` | Integer, NOT NULL, default 0 | upsert로 +1 |
| `created_at` / `updated_at` | TimestampMixin | 카운터 행 메타(개별 이벤트 시각 아님) |

- 유니크 제약: `uq_safety_event_type_day (event_type, day_bucket)` — 하루·종류당 1행.
- **user_id/FK 없음** → 정신건강 데이터와 물리적으로 무관한 순수 집계 테이블.
- `day_bucket`은 기존 KST 유틸 재사용(`e42cafd` KST 주차 버그와 일관). UTC 자정 넘김 버킷 오분류 방지.

## 4. 적재 서비스

신규 `app/services/safety_metrics.py` — `record_safety_event(event_type: str) -> None`.

핵심 원칙 3가지:
1. **독립 세션** — 요청 `db`를 받지 않고 자체 `AsyncSessionLocal`. 계측이 평가/챗봇 트랜잭션에 끼어들어 롤백시키는 일 차단(BackgroundTask 원칙과 동일).
2. **예외 삼킴 (best-effort)** — 계측 실패는 `warning` 로그만. 평가 저장·챗봇 응답이 계측 때문에 절대 5xx 안 남.
3. **DB-레벨 원자적 upsert** — `pg_insert(...).on_conflict_do_update(count = count + 1)`. 동시 요청이 같은 버킷을 쳐도 경합 없이 정확.

```python
async def record_safety_event(event_type: str) -> None:
    try:
        async with AsyncSessionLocal() as db:
            stmt = pg_insert(SafetyEventCounter).values(
                event_type=event_type, day_bucket=today_kst(), count=1,
            ).on_conflict_do_update(
                index_elements=["event_type", "day_bucket"],
                set_={"count": SafetyEventCounter.count + 1, "updated_at": now_utc()},
            )
            await db.execute(stmt)
            await db.commit()
    except Exception:
        logger.warning("safety metric drop: %s", event_type)
```

## 5. 호출 지점 (5종, 각 한 줄 · 기존 로직 불변)

| event_type | 위치 | 타이밍 |
|---|---|---|
| `crisis_flag_phq9` | `api/v1/assessments.py` | 평가 `db.commit()` **이후**, 9번 양성(`needs_professional_flag`) |
| `crisis_tier4` | `api/v1/assessments.py` | 같은 지점, `tier == 4` |
| `chat_guard_input` | `services/chat.py` 입력단 | `detect_crisis(message)` True 분기 |
| `chat_guard_output` | `services/chat.py` 출력단 | `detect_crisis(reply)` True → CRISIS_REPLY 교체 |
| `chat_banned_term` | `services/chat.py` 출력단 | `is_reply_safe(reply)` False → SAFE_FALLBACK 교체 |

- assessments는 커밋 이후 호출(계측 실패가 평가에 영향 0).
- chat은 `handle_message` 흐름 내 `await record_safety_event(...)`. 단일 upsert·독립세션이라 응답 지연 무시 가능.
- **한 요청 1카운트 보장**: `crisis_info_shown`(핫라인 노출)은 별도 카운트하지 않는다 — 가드 발동의 종속 결과라 이중집계가 되기 때문. 챗봇 핫라인 노출수 = `chat_guard_input + chat_guard_output` 합. 입력단/출력단은 상호배타(입력에서 잡히면 LLM 미호출). 평가 결과화면 핫라인 노출은 `crisis_flag_phq9`/`crisis_tier4`가 대표.
